# Full-Stack SaaS Starter Kit: quality report

> **Where the code is.** The measurement scripts that produced these results are part of the source package, which is distributed separately (see [SOURCE-ACCESS.md](../SOURCE-ACCESS.md)). The raw results they wrote are included in this repository under [`results/`](../results/).

Version 0.1.0 by The Diamond Empire (<https://thedempire.shop/>). This report states what was measured, how, what the numbers were, and what the checks cannot tell you. Every number in the results block comes from a file in [results/](../results/) that a script in this repository wrote; the block is generated by `npm run results:tables` and a test fails if it drifts. Timing is deliberately not reported: the machine that built this is shared and loaded, and the experiments use a simulated clock.

**Read this first.** The database in every test and experiment is **PGlite**, PostgreSQL compiled to WebAssembly and running in-process. **Nothing here was run against a real PostgreSQL server**, so row-level security and tenant isolation are verified on PGlite only. **Stripe was never called**: billing ran on an in-process simulator, and webhook signatures were only checked against this repository's own signer. No email provider, OAuth provider, Docker, Terraform or cloud account was available. The Dockerfile, the compose file, the Terraform and the CI workflow were never run.

## Verdicts

These sentences interpret the tables above; the tables are the source of truth.

- **Tests:** all tests passed in the clean-copy run (see the test table). They run on PGlite, the Stripe simulator, a fake OAuth provider and a development mailer; they show the logic behaves as written against those stand-ins, not against the real services.
- **E1, tenant isolation:** on the real schema the fuzzer found no violation and no row-count drift in its random operations (reads, explicit foreign filters, updates, deletes, inserts claiming another tenant, joins, no context, user context without an organization). The canary run on a deliberately broken schema reported violations in exactly the tables that were broken (`projects`, `usage_events`) and in the cross join over them, and row-count drift, so the harness can see a leak of the kinds it generates. This is evidence on PGlite for the operations generated, with synthetic data, six tenants and one seed. It is not proof that no leak exists and says nothing about a real PostgreSQL server.
- **E2, webhook replay:** in scenario A (every event in its own second) the subject database ended in the same state as the in-order oracle for every subscription and invoice, with about 60% of deliveries being duplicates, many events arriving stale, bursts of concurrent deliveries and no failed event; the total paid amount matched exactly. **Scenario B is a negative result for the ordering rule:** when events about one subscription share a second, 10 of 60 subscriptions ended in a different state than in-order application, because one-second `created` times cannot order them. Invoices were unaffected, and `reconcile()` repaired all 10 subscriptions from the Stripe-side state. Whether real Stripe traffic produces such ties at a meaningful rate is not known.
- **E3, rate limiting:** over the 42 limit-and-pattern cases the limiter made exactly the same decision as the independent exact reference every time, never admitted more than capacity plus refill times elapsed time, and the HTTP route admitted exactly 600 of 650 simultaneous requests and then exactly 60 of 70 after six simulated seconds. This shows the arithmetic is exact in the model; it says nothing about real clocks, several instances or load.
- **Licenses:** every package in the production tree is permissive (MIT, ISC or Apache-2.0). Fourteen development-only packages (a WebAssembly HCL parser and the lightningcss binaries pulled in by the test runner under MPL-2.0, and one package under BlueOak-1.0.0) are outside the permissive set the check uses; none is shipped.
- **Dependency audit:** the registry reported no known vulnerabilities in the production tree on the day of the run. Development tools were not audited.
- **Repository scan:** no absolute local path, user name, stray name, secret, code file under `docs/` or `results/`, broken link or missing README structure.
- **Colour contrast:** all 20 colour pairs from the console's style sheet reach 4.5:1 in both schemes. This is not an accessibility result for the console.
- **Compiled server:** the built output starts, answers its health, readiness, console and sign-up endpoints on localhost and stops. It says nothing about the Docker image or a deployment.

## Limits and threats to validity

- **PGlite is not a PostgreSQL server.** It is the PostgreSQL engine compiled to WebAssembly with one connection. Tenant-isolation tests, the fuzz run, advisory-lock behavior and the node-postgres adapter tests say nothing about a real server's behavior under connection pooling, concurrent connections, lock contention, other major versions, extensions or managed-database restrictions (for example how a managed provider treats `CREATE ROLE`). With one connection, the concurrency tests (parallel webhook deliveries, parallel role changes, parallel audit writers) exercise application-level locking and `FOR UPDATE` only in a serialized setting.
- **The node-postgres adapter** ran only against PGlite served over the PostgreSQL wire protocol, with a pool of one connection.
- **Stripe was never called.** The simulator models the behavior described in this repository, not Stripe's. Event shapes, field names, the signature scheme, timing and ordering guarantees, proration rounding, trial and dunning behavior come from public descriptions as understood by the author. The signature code was tested only against the repository's own signer. A real client was not written.
- **Event ordering is partly a modeling choice.** E2's scenario A gives every event its own second; scenario B creates same-second ties. Real Stripe traffic has its own timing. The `created` field has one-second resolution, which is the cause of the residual mismatches in scenario B.
- **The fuzz harness found nothing, which is only as meaningful as its reach.** E1's canary shows it can see a leak of the kinds it generates; it cannot see a leak through an operation it does not generate. It covers the tenant tables and a fixed set of operation types, with synthetic data, 6 tenants and a fixed seed.
- **Rate-limit accuracy is checked on a simulated integer-millisecond clock.** Real clocks, event-loop delays, multiple instances and clock changes are not covered, and the in-process store is per instance.
- **Browser and accessibility.** The console was opened by hand in one browser during development. No automated browser test, no screen reader and no accessibility tool was used. The contrast check covers 20 colour pairs from the style sheet and says nothing about layout, keyboard use, focus order, labels or zoom. Nothing here is a statement of conformance with any accessibility standard.
- **Security.** The [security checklist](security-checklist.md) is a self-assessment against the application-security topics of OWASP ASVS Level 1, not an audit. No penetration test, no static-analysis tool beyond the type checker and ESLint's recommended rules, no route-level fuzzing, no load test.
- **Dependency audit** depends on the advisory database on the day it ran and needs the npm registry; the result file says whether it could run.
- **Deploy files.** The Terraform was parsed as HCL syntax only (references and variable use are checked by a test); it was never validated by Terraform, never planned and never applied. The Dockerfile and the compose file were never built or run. The CI workflow was never executed.
- **Migration linter** is a text heuristic over statements, not a SQL parser; the runner is transactional, so concurrent index builds are not supported by it.
- **The audit chain does not detect truncation of its newest records** (tested and disclosed), and it is not anchored outside the database.
- **Shared machine.** Other jobs were running during the work. This does not affect pass/fail checks, counts or byte sizes, and is why no timing is reported.
- **Not measured:** request latency, throughput, memory, startup time, behavior under load, real-user behavior, email deliverability, payment success rates.

## Change log

Disclosure of reruns and changes made after something was measured or found.

1. **Authoring order.** The code was written in milestone order (M1 to M5) with its tests, and each milestone's tests were run before the next. The audit log and the job queue's email use were built early because the first milestone needed them, and their dedicated tests came with M3 and M4.
2. **Problems the tests found, fixed before the final run.** Tenant transactions could not enqueue mail because the job table had no grant for them: it became an insert-only "outbox" class with its own catalog test. The first API-key guessing guard was a per-address limit on all key traffic and throttled legitimate callers: it now counts failed attempts only. An early rate limiter used floating-point refill: it was rewritten in integer arithmetic before E3 existed. The console rendered form fields as object text until it was opened in a browser: fixed. A slug function left stray hyphens for accented letters. Several tests had mistakes (a shared simulator left switched off between tests, a timing assumption about the clock, a test that asserted on a swallowed aborted transaction).
3. **Late additions that changed the design.** After the Terraform example was drafted it was clear it would deploy an application with no networked database adapter, so a node-postgres adapter, a `DATABASE_URL` setting and production start-up guards were added (production refuses weak or default secrets, a missing database URL, and the billing simulator unless acknowledged). The adapter was tested against PGlite over the wire protocol, not a real server.
4. **A scanner bug found by testing the scanner.** The repository scan's pattern for Windows drive paths had an escaping mistake and only matched forward slashes. A synthetic-input test exposed it; the pattern was fixed before the measured runs, and the scan was then clean.
5. **A runner problem unrelated to the code.** On this machine the test runner's module cache failed with a rename error (EPERM) for one source file, reproducibly, until the comment text in that file changed. The cause was not identified (an antivirus lock is the likely suspect); no behavior changed.
6. **Exploratory runs.** The test suite, a smoke version of the experiments, the compiled server and the console were run several times on the development folder before the measured runs. Those outputs were not recorded. The experiment generator and the canary attribution were corrected after smoke runs (a simulated lifecycle continued after a subscription had ended; cross-join violations were attributed to a random table), before the measured runs.
7. **Three complete measured runs, two superseded.** The full measurement set was run from a fresh clean copy three times. In the first two, only the compiled-server smoke step failed, and only because of the smoke script's own test data: its sign-up probe used a password that contained the account's email name, which the password policy correctly rejected (HTTP 400 instead of 202). Everything else passed in all three runs (all 400 tests, the experiments, the scans). The script was corrected and the whole set rerun from a new clean copy; only the third run is in `results/`. The first two runs' outputs were kept outside the repository and are not used. Their headline numbers for the experiments were the same as in the third run (experiments are seeded and deterministic): E1 3,574 operations with no violations and 982 canary violations, E2 scenario B 10 mismatches, E3 no decision differences, 400 of 400 tests.
8. **After the measured run.** Only documentation, the generated tables and the wording of the "Environment" lines in `scripts/results-tables.ts` changed. The README phase moved from Prototype to Beta once the results were in. A final clean-copy run of `npm run check` and `npm run scan:repo` (which includes the check that the tables match `results/`) was made on that final state; its output is not recorded in `results/`.
